## 1-CN. 2026-09-02 세션 — 프로젝트 상위 폴더에서 워크스페이스를 여는 중첩 구조 지원 (정의/참조의 컴파일 단위 경계)

### 증상 / 요청

사용자 확정 구조:

```text
C:\SVN\pa\trunk\develop\07. Others\37. 핵산 Oligo 합성과제\시뮬레이션\projects\GPL_Code\Project.gpr
                                                                                       \Main.gpl
                                                                                       \Lib_Net\Project.gpr
                                                                                       \Lib_Core\Project.gpr
```

깊은 중첩 + 공백 + 한글 + 점(`07.`/`37.`)이 든 폴더명, SVN 작업 사본 안, **라이브러리가 메인 프로젝트 폴더
안에** 들어가는 배치. "이런 구조에서도 문제 없이 동작하는지 검토 후 개선" — 특히 **정의 찾기·참조 찾기**가 걱정.

### 원인 (코드 확인)

먼저 **경로 자체는 문제가 아니었다.** `.gpr` 탐색은 `**/*.gpr` 글롭과 `path` API 기반이라 깊이·문자와 무관하고,
`listSourceFilesRecursive`의 `maxDepth`는 **프로젝트 폴더 기준 상대 깊이**(16)라 워크스페이스가 깊어도 걸리지 않는다.
경로를 글롭 패턴에 끼워 넣는 곳도 없다(include는 항상 `**/*.gpl` 고정, `RelativePattern` 미사용). 중첩 라이브러리도
`projectSources.ts`(§1-CK 이후)가 이미 다룬다.

**진짜 문제는 워크스페이스를 프로젝트 폴더가 아니라 상위(`…\시뮬레이션`, `…\develop`)에서 열 때** 드러났다.
그러면 인덱스에 여러 과제의 프로젝트가 함께 들어오는데, 사내 템플릿을 복제해 쓰는 구조라 **폴더명·ProjectName·
소스 파일명까지 같다**(`GPL_Code/Main.gpl`이 과제마다 있다).

① **정의 찾기 — 프로젝트 경계가 "점수"일 뿐 "필터"가 아니었다.** `symbolCache.pickBestCandidate()`는
`scoreFilePath()`의 최고점 후보를 **무조건** 돌려준다. 점수는 순위이지 경계가 아니어서, 같은 이름이 다른 과제
프로젝트에 있으면 `SCORE_UNRELATED`(0)여도 최선 후보가 되어 **무관한 프로젝트의 정의로 점프**했다.

② **`ProjectLibrary` 관계가 "같은 프로젝트" 점수에서 빠져 있었다.** `SCORE_SAME_PROJECT`(650)는 소유 `.gpr`
폴더 **하위**만 인정한다. `GPL_Code\Lib_Net`은 하위라 우연히 맞았지만, 형제 폴더 배치(`projects/Lib_*`)의
라이브러리 정의는 `SCORE_UNRELATED`로 떨어져 **최상위 폴더만 같은 남의 프로젝트**(`SCORE_SAME_TOP_LEVEL_FOLDER`
= 500)에게 진다.

③ **참조 찾기는 정의 파일을 기준으로 범위를 잡는다.** `resolveProjectFileScope(targetFilePath)`는 제대로
프로젝트+라이브러리로 좁히지만, 그 `targetFilePath`가 ①에서 오염되면 **엉뚱한 프로젝트를 뒤진다.**
최후 폴백인 `symbolCache.findReferences()`는 인덱싱된 **전 파일**을 이름만으로 훑어 경계가 아예 없었다.

④ **이름 바꾸기(F2)가 워크스페이스 전체의 문자열을 고쳤다.** `renameProvider.addStringLiteralEdits()`가
`findFiles('**/*.gpl')`로 워크스페이스 전체를 스캔해, `"Mod.Proc"` 문자열 참조를 **다른 과제 프로젝트에서도**
바꿨다. 되돌리기 어려운 편집이라 가장 위험했다.

⑤ **`.svn`이 탐색 제외 목록에 없었다.** `findFiles(include, exclude)`는 exclude를 **명시하면 `files.exclude`
기본값이 적용되지 않는다**(VS Code API 규약). 기본값에 있던 `**/.svn`이 통째로 스캔 대상이 됐다 — 하필
경로가 `C:\SVN\…`이다. 같은 목록이 `deployService`·`referenceProvider`·`renameProvider`에 제각각 복사돼 있었다.

⑥ **워크스페이스 전역 재귀 스캔에 상한이 없었다.** `gplDebugSession._scanDir/_findFiles`와
`extension.ts findWorkspaceFilesByName`은 동기 `readdirSync` 무제한 재귀다. `develop` 같은 상위 폴더를 열면
수만 개 폴더를 확장 호스트 스레드에서 훑어 UI가 멈춘다.

### 조치 (의도와 방법)

**① 컴파일 단위 경계를 단일 출처로 — `src/project/compileUnit.ts`(신규, vscode 무의존)**

`CompileUnitIndex`가 "이 파일과 함께 컴파일되는 프로젝트 폴더들"을 답한다. 규칙 자체는 기존
`projectSources.collectRelatedGprPaths()`(자기 `.gpr` + `ProjectLibrary` 재귀 + 역방향 참조자)가 그대로 정본이고,
이 모듈의 역할은 **캐시**다 — 정의 후보 선택은 후보마다 불리므로 `.gpr`를 매번 읽으면 안 된다.
`.gpr` 목록이 실제로 바뀔 때만 캐시를 버린다.

**판정 불가는 빈 배열**로 답한다(워크스페이스에 `.gpr`가 없거나 파일이 어느 프로젝트에도 안 속함).
호출측은 그때 **좁히지 않는다** — 경계를 모를 때 후보를 지우면 정의를 통째로 놓친다(누락 방지 우선).

**② 정의 후보를 컴파일 단위로 자른다 — `narrowToCompileUnit()`**

단위 **안**에 후보가 하나라도 있으면 밖의 후보를 전부 버린다. GPL은 단일 이름 공간이라 같은 컴파일 단위에서
이름이 풀리면 그것이 정의이고, 다른 프로젝트의 동명 심볼은 정의가 될 수 없다. 단위 안 후보가 하나도 없으면
원본을 유지한다. `findDefinitionMatches()`와 `pickCallableMatches()`(클래스/모듈 멤버 폴백 — 여기가 전 파일을
훑던 자리다) 양쪽에 적용했다.

**③ 점수 체계에 `SCORE_RELATED_PROJECT`(600) 추가** — `SAME_PROJECT`(650)와 `SAME_TOP_LEVEL_FOLDER`(500) 사이.
라이브러리 관계로 함께 컴파일되는 프로젝트가 남의 프로젝트를 이긴다. (`isSameUnit()`은 "모르면 true"라
점수 매기기에는 못 쓴다 — 점수는 단위가 **확정된** 경우에만 준다.)

**④ 참조 찾기 결과를 단위 밖으로 흘리지 않는다** — `referenceProvider`에 `inCompileUnit()` 게이트를 두고
워크스페이스 텍스트 검색 결과와 캐시 폴백 결과 양쪽에 적용. **①이 고쳐지면 기준 파일이 정확해지므로
참조 범위도 따라서 정확해진다** — 이게 사용자가 걱정한 지점의 실제 수리 경로다.

**⑤ 이름 바꾸기의 문자열 스캔을 컴파일 단위로 좁혔다** — `addStringLiteralEdits()`가
`resolveProjectFileScope(정의 파일)`을 쓴다. 상한(300)에 걸리면 로그로 알린다.

**⑥ 제외 목록 단일 출처화 + `.svn`/`.hg`/`CVS` 추가** — `PROJECT_EXCLUDE_GLOB` 하나를 `deployService.findProjectDirs`·
`referenceProvider`가 함께 쓴다(`renameProvider`는 ⑤로 글롭 자체가 사라졌다).

**⑦ 상한 있는 공용 재귀 순회 — `projectSources.walkTree()`** (깊이 24 / 디렉터리 20000, 걸리면 `truncated`).
`isSkippedScanDir()`도 여기로 모아 디버그 소스맵·트리 명령이 같은 규칙을 쓴다. 상한에 걸리면
"프로젝트(또는 projects) 폴더를 워크스페이스로 여세요"를 로그로 안내한다 — 조용히 자르지 않는다.

**⑧ `.gpr` 파일 워처 추가**(`extension.ts`) — `.gpr`는 "어떤 파일이 같은 컴파일 단위인가"를 정의하므로,
바뀌면 경계 캐시를 버리고 심볼 인덱스를 다시 만든다(800 ms 디바운스 — 저장·SVN update 연타 대비).

### 부수 발견 — `fs.rmSync`가 비ASCII 경로에서 Node를 죽인다

테스트가 원인 불명으로 죽어 추적한 결과, **Node v24.11.1(Windows)에서 `fs.rmSync()`의 경로 인자에 비ASCII
문자가 있으면 프로세스가 즉시 죽는다** — 예외도 `exit` 이벤트도 없이 `0xC0000409`
(STATUS_STACK_BUFFER_OVERRUN). 샌드박스 밖(PowerShell)에서도 동일하게 재현된다.

```text
fs.rmSync('…/ascii/a.gpr')           → OK
fs.rmSync('…/시뮬레이션/a.gpr')      → 프로세스 사망 (파일/디렉터리, force·recursive 무관)
fs.rmSync('…/ascii/한글.gpr')        → 프로세스 사망
fs.unlinkSync('…/시뮬레이션/a.gpr')  → OK
fs.rmSync('…/ascii-root', {recursive:true})  → OK (하위에 한글 폴더가 있어도 됨 — 인자 자체가 ASCII면 안전)
```

- **확장 런타임 소스에는 `fs.rmSync`가 없다**(전부 `fs.unlinkSync`) → 사용자 영향 없음.
- `scripts/clean.js`만 `fs.rmSync(abs, {recursive:true, force:true})`를 쓴다. 지금 저장소 경로는 ASCII라 무해하지만,
  **한글 경로에 클론하면 `npm run clean`이 크래시**한다. → **§1-CU 에서 고쳤다**
  (ASCII 경로는 종전 native 경로, 비ASCII 경로만 `unlinkSync`/`rmdirSync` 폴백).
