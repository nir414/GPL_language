## 1-EH. 2026-10-02 세션 — GPL 4.2K5의 Catch 없는 Try를 편집기에서 경고

### 증상·원인

사용자가 **제어기의 GPL 4.2K5**에서 `Try...Finally`만 작성(Catch 생략)하면 Finally가 다시 실행되고,
Finally 안에서 Object 정보도 잃는 이상 동작을 실기에서 관측했다. 컴파일러 버그라는 원인 판단은
아직 추정이다. 이 제약은 확장이 분석하는 **GPL 소스**에 적용하며 확장 구현 언어인 TypeScript의
Try/Catch 작성 규칙과는 별개다.

기존 확장에는 Catch 누락 검사가 없었다. 모든 정적 진단이 `gpl.diagnostics.experimental`(기본 false)
뒤에 있어, 그 경로에만 경고를 추가하면 기본 설정에서는 보이지 않는 문제도 있었다.

### 조치

- `language/tryCatch.ts`(순수)에서 Catch 없는 Try를 검출한다. 각 중첩 Try의 Catch를 따로 추적하며
  기존 GPLParser의 문자열·주석 제거와 논리 줄 병합을 사용한다. Finally 또는 End Try를 만난 뒤
  해당 Try 키워드에만 경고한다. 입력 중인 Try 단독에는 경고를 미루며 프로시저 경계를 넘지 않는다.
- `diagnosticProvider`가 `try-without-catch`를 **Warning**(`GPL Compatibility`)으로 표시한다.
  `gpl.diagnostics.tryWithoutCatch`(resource, 기본 true)로 이 경고만 끌 수 있다. 실험 진단의 기존
  기본 비활성 동작은 유지하고 문서 열기·편집·저장 시 Catch 경고는 기본 실행한다.
- 진단 설정 변경 시 열린 GPL 문서를 재검사한다. XML 분석 명령의 비활성 안내도 실험 XML 진단을
  가리키도록 좁혔다. Try/Finally 문 완성 안내는 동일한 GPL 4.2K5 설명 상수를 사용하고 README에
  경고 동작·설정을 기록했다. Try 스니펫은 이미 Catch를 포함하므로 삽입 형태는 유지했다.
- 제어기 버전을 자동 조회하지 않는다. 연결 없이 GPL 소스를 편집할 때도 경고하며, 메시지에
  **GPL 4.2K5에서 관측된 제약**임을 명시한다. 다른 버전에서의 발생 여부는 확인하지 않았다.

### 검증

- Windows 로컬 `npm test`: **1066/1066 통과**(TypeScript compile 포함, 기존 1045 + 신규 21건).
- 순수 검사 15건: 정상 Catch, Finally 없는 누락, 중첩별 소속, 주석·문자열, 대소문자·CRLF·줄 연속,
  입력 중 코드·프로시저 경계, Catch 추가 시 해소와 문 완성 안내를 검증했다.
- 실제 컴파일된 diagnostic provider를 VS Code API 대역으로 실행한 6건: 실험 설정을 켜지 않은
  기본 경고·Warning 범위, 편집 후 생성/제거, 경고만 비활성화·실험 진단 유지, 설정 변경 후 재검사,
  디바운스·삭제 정리, TypeScript 문서 제외를 검증했다.
- 패키징·설치·F5 창 실행·제어기 명령·실기 재현은 수행하지 않았다.

### 남은 일

## 1-EI. 2026-10-02 세션 — 개요(Outline) 검토: 종류 분류·detail 시그니처·`Ctrl+T` 위치, 표현 모델을 순수 모듈로

### 계기 (사용자 요청)

VS Code Outline 사용법 목록(개요 패널 상시 표시 · `Ctrl+Alt+F` 이름 필터 · `outline.showXXX` 종류 필터 ·
`Ctrl+Shift+O` · `@:` 종류별 묶음)을 주고 "개선 가능한 부분을 검토한 뒤 개선" 을 요청했다. 제어기 무관, 편집기 기능만.

### 검토 결과 — 무엇이 어긋나 있었나

- **종류(`SymbolKind`) 분류가 VS Code 의 필터·묶음 의미와 어긋났다.** Sub→Method, Function→Function 으로 고정돼 있어
  `outline.showMethods` 를 끄면 Sub 만 사라지고 Function 은 남았고, `@:` 묶음도 "methods/functions" 가 **반환값 유무**로
  갈렸다. 멤버 변수는 Variable(VS Code 에서는 지역 변수 범주)이라 `outline.showVariables`/`showFields` 가 뜻과 달랐다.
- **detail 이 반환 타입뿐이었다.** 동명 오버로드(`Shapes.gpl` 의 `Describe` ×3)가 개요·`Ctrl+Shift+O` 에서 똑같이 보였고
  Sub 는 아무 정보가 없었다. `Shared`·`ReadOnly`/`WriteOnly`·상수 값도 보이지 않았다.
- **`Ctrl+T` 워크스페이스 심볼**: 위치가 줄 머리(`Position(line, 0)`)라 이동 후 커서가 들여쓰기 앞에 놓였고, 질의가
  연속 부분 문자열(`includes`)이라 VS Code 의 퍼지 기대와 달랐다(`rlog` 로 `RegisterLogSink` 를 못 찾음). 종류 대응표가
  개요 provider 와 **별도 사본**(switch 두 벌)이라 R7(SSOT) 위반 소지였고, 로컬 심볼을 거르지 않았다.
- **입력 중 블록(짝 `End` 없음)의 범위 폴백**(`findSymbolEndLine`)이 중첩 클래스를 몰라 형제 범위가 겹칠 수 있었다
  (§1-ED 의 "남은 일").
- 잘 돼 있던 것: 계층·범위(§1-ED), `Ctrl+Alt+F` 필터·정렬·커서 따르기는 VS Code 코어가 이름/`range` 로 처리 —
  provider 쪽은 이름·범위만 정확하면 된다.

### 조치

- **`language/outlineModel.ts` 신설(순수)** — 개요·`Ctrl+Shift+O`·`Ctrl+T` 가 공유하는 표현 모델.
  - `outlineCategoryOf`: 클래스 멤버 Sub/Function → `method`, 모듈 프로시저 → `function`, 멤버 변수 → `field`,
    로컬·파라미터 → `variable`, Delegate → `delegate`(아이콘은 §1-DU 결정대로 Class), 그 외 module/class/property/constant.
  - `symbolDetail`: `(a As Integer, b As String) As String`(ByVal 은 지우고 ByRef 는 남김), `As Integer (ReadOnly)`,
    `As Integer = 1000`, `Shared As Integer`, `Delegate Sub (text As String)`, 배열은 GPL 표기 `As Integer()`
    (요소 타입 벗기기는 R7 정본 `receiverType.elementTypeOf` 사용). 모듈·클래스는 빈 문자열.

## 1-ER. 2026-10-19 세션 — Debug Console 여러 줄 실행 + 상태 변경 명령 미전송 안내

### 계기·판단

사용자가 메모해 둔 기능 개선 항목을 참고해 확장을 자율 개선해 달라고 요청했다. §3에서 제어기·F5 실기 확인만 남은 항목은
이번 자동 작업으로 닫을 수 없으므로, 제어기 없이 구현·검증할 수 있고 실제 불편이 기록된 Debug Console 항목을 골랐다.

기존 REPL은 입력 전체를 하나의 식으로 다뤄 여러 명령을 붙여 넣을 수 없었다. 또 `Break`·`Stop`·`Execute` 같은 상태 변경 명령은
안전 정책상 `>` 접두사가 없으면 원문 명령을 보내지 않는 것이 맞지만, 최종 문구가 "변수 평가 실패" 위주라 사용자는 이미 보낸 줄로
오해할 수 있었다. 정책을 느슨하게 하지 않고, 입력 단위와 결과 표시를 명확히 하는 방향으로 정했다. 별도 "진단 묶음" 명령은 만들지
않았다 — 여러 줄 붙여넣기가 임의의 읽기 명령 조합을 그대로 수용해 고정 워크플로를 추가할 필요가 줄기 때문이다.

### 조치

- `debug/replInput.ts`(순수) 신설: CRLF/LF 입력을 빈 줄 제외·원래 순서로 분리하고, 줄별 `>` 접두사 제거,
  상태 변경/파괴적 명령의 미전송 안내, 입력별 결과 블록 렌더링을 맡는다.
- `gplDebugSession.evaluateRequest`: 여러 줄이면 각 줄을 기존 단일 입력 정책(변수 평가 → 읽기 전용 명령 폴백,
  `>`는 강제 전송)으로 순차 처리한다. 강제 전송할 비읽기 명령이 여러 개여도 `gpl.debug.confirmDestructiveRepl` 확인은
  묶음 전체에 한 번만 하고, 취소하면 일부 읽기 명령도 먼저 나가지 않도록 전체 입력을 실행 전에 중단한다.
- 단일/여러 줄 모두 `>` 없는 `Break`·`Stop`·`Execute` 등은 "이 입력을 제어기 명령으로 보내지 않았다"와 올바른
  `>명령` 예를 먼저 표시한다. 변수/전역 조회 시도와 원문 상태 변경 명령 전송을 혼동하지 않도록 "통신 없음"이라고 표현하지 않았다.
- README와 제어기 디버깅 런북에 여러 줄 입력·접두사·묶음 확인 규칙을 함께 기록했다.

   완료 알림을 선택하거나 닫기 전까지 진행 표시가 남는다. 전송 지연이 아니라 UI 수명주기 문제다.
2. **「폴더 열기」와 첫 「워크스페이스에 추가」 모두 현재 연결을 유지하지 않는다.** 「폴더 열기」의 `vscode.openFolder(localDir)`는
   Extension Development Host를 다시 열었다. 「워크스페이스에 추가」의 `updateWorkspaceFolders`는 같은 창에 `hello-project`와
   `EM2RS_Probe`를 만들었지만, VS Code API가 명시한 단일 폴더→다중 루트 전환 재시작으로 확장이 비활성화됐다.
   `extension.ts:176~181`의 `deactivate()`는 제어기 연결을 닫으므로 자동 연결 해제는 현재 구현상 정상 결과다.
   전환 뒤의 제목 없는 다중 루트 작업 영역을 닫으면 `.code-workspace` 저장 여부를 묻고, 「저장 안 함」은 파일이 아니라 작업 영역 구성을 버린 뒤 창 닫기를 계속한다.
3. **새 temp 폴더가 제한 모드로 열린다.** 타임스탬프 폴더를 계속 만들면 Workspace Trust를 매번 확인해야 한다.
   두 번째 루트 `Lib` 추가 때도 「이 폴더에 있는 파일의 작성자를 신뢰합니까?」가 나타났다. `%TEMP%` 전체 신뢰는 범위가 너무 넓으므로,
   전용 고정 스냅샷 루트를 한 번 신뢰하는 설계가 더 안전하다.
4. **같은 다운로드 폴더를 재사용하면 잔여 파일이 섞일 수 있다.** `downloadProject`는 원격 파일을 덮어쓰지만 로컬에만 남은 파일은 지우지 않는다.
   다른 제어기·다른 시점의 스냅샷은 새 디렉터리 또는 스테이징 디렉터리에 받아야 한다.
5. **현재 다운로드 폴더는 읽기 전용 Snapshot이 아니라 제어기 `/GPL`과 왕복하는 Live Working Copy다.** `package.json`의 `gpl.quickCompile.autoOnSave` 기본값 `auto`는
   `/GPL/<project>` 존재 시 저장 파일을 먼저 업로드하고, 제어기가 완전 STOP이 아닐 때 Compile만 보류한다. `deploy.ts`의
   `onDidSaveTextDocument`도 연결 상태에서 모든 GPL 저장을 이 경로에 넣는다. 수동 저장뿐 아니라 VS Code Auto Save도 같은 위험이 있다.
6. **중첩 프로젝트의 언어 범위와 배포 단위가 결합돼 있다.** autoOnSave 대상은 파일을 포함하는 가장 깊은 `.gpr` 폴더를 선택하므로,
   원격의 단일 `/GPL/Lib` 스냅샷 안에 여러 내부 프로젝트가 있는 구조에서 `Lib_Log` 같은 존재하지 않는 최상위 원격 프로젝트를 만든다.

### 설계 판단

FTP 다운로드 흐름 자체에서 산출물을 **Live Working Copy**로 볼지 **Read-only Snapshot**으로 볼지 먼저 고르게 한다.
현재처럼 `/GPL` 작업 소스에 변경을 왕복하는 시험 흐름에서는 autoOnSave가 의도에 맞고, 영구 저장은 별도의 Save to Flash 경계로 유지한다.
재현·비교용 Snapshot은 manifest를 근거로 원격 쓰기를 막고 불변 원본을 보존한다. 두 모드는 제어기 주소·원격 경로·수집 시각·
파일 수/크기/해시 manifest와 저장된 작업공간 흐름을 공유한다.
현재 Attach는 기본값으로 제어기 프로젝트 브레이크포인트를 정리할 수 있으므로 “다운로드 후 자동 Attach”를 곧바로 묶지 않는다.

### 구현

- `project/controllerProjectWorkspace.ts`를 추가해 `.gpl-controller-project.json` 스키마, 파일 SHA-256 수집,
  ancestor manifest 탐색, 중첩 프로젝트 루트 접기, 기존 사본 비덮어쓰기, staging 경계 삭제, 저장된 작업공간 생성을 한 곳에 모았다.
- `ftpCommands.ts`는 Live Working Copy/Read-only Snapshot을 선택하고 빈 staging에서 다운로드한 뒤 manifest를 기록해 완성 폴더로
  rename한다. 완료 알림은 `withProgress` 밖에서 띄운다. 작업공간은 프로젝트별 다중 루트가 아니라 선택한 상위 폴더 하나를 루트로 해,

  `projectFileScope`/compile-unit 규칙을 그대로 사용하므로 내부 심볼 탐색 범위와 원격 배포 단위를 분리했다.

## 1-FB. 2026-10-21 세션 — 트리의 불편한 DIO 조회/설정을 대시보드 디지털 I/O 제어판으로 통합

### 요청·판단

사용자는 GPL Controller Status View의 I/O 조작이 불편하므로 커스텀 UI 패널로 옮기고 상태도 직관적으로 보이게 해 달라고 했다.
기존 트리는 `Show DIO` 입력창과 `Set DIO`의 신호 입력 → 동작 QuickPick → 확인 모달을 각각 열어야 했고, 조회 결과도 Output 원문뿐이라
여러 신호의 현재값과 강제 상태를 비교하기 어려웠다.

별도 Webview를 하나 더 만들기보다 이미 상태·폴링 수명주기·연결 세션 게이트를 가진 제어기 대시보드에 `상태 / 디지털 I/O` 탭을 두었다.
상태 탭과 I/O 탭 중 현재 탭의 데이터만 폴링해 `Show DIO`를 기존 자원 프로브에 추가로 계속 보내지 않으며, 트리에는 두 원시 명령 대신
제어판 진입점 하나만 둔다. `showDio`·`setDio` 명령 ID는 팔레트·URI·외부 호출 호환성을 위해 유지했다.

### 공식 명령 의미 확인

- Brooks 문서 검색 스킬의 오프라인 topic cache에서 `Show DIO`·`Set DIO`를 검색해 공식 Console Command 페이지를 찾고,
  두 페이지 본문을 직접 확인했다(검색 mode `cache`, direct URL access 성공, 의미 해석 신뢰 높음).
- `Show DIO` 인자 생략은 설치된 모든 신호를 표시하고 행은 `signal_number: 0|1`, 뒤의 `*`는 특정 상태로 강제됐다는 표시다.
- `Set DIO signal value`: `1`=강제 ON, `-1`=강제 OFF, `0`/생략=현재 신호값을 바꾸지 않고 강제 해제다. 명령은 출력뿐 아니라
  디지털 입력 또는 출력 신호의 강제 상태를 바꿀 수 있으므로 기존 사용자 문구 「DIO 출력 설정」을 「DIO 강제 상태 설정」으로 바로잡았다.

## 1-FC. 2026-10-21 세션 — 실행 중 프로그램을 건드리지 않는 Upload Only와 제어기별 순차 배포 큐

### 요청·판단

실행 중인 프로그램을 정지·컴파일·재시작하지 않고 `/GPL` 작업 소스만 갱신하는 명시적 경로와, 같은 제어기에 여러 프로젝트를
연달아 요청했을 때 사용자가 다시 실행하지 않아도 등록 순서대로 처리하는 대기열이 필요했다. 기존 옵션 조합으로 뜻을 숨기지 않고
`uploadOnly` 모드를 공개 계약으로 두었으며, 실행 중 원격 전용 파일 삭제는 안전성이 확인되지 않아 보류한다.

## 1-FD. 2026-10-21 세션 — Save to Flash 중 전원 차단 금지 경고와 안전 확인

### 요청·판단

사용자는 제어기가 flash 메모리를 저장하며 Busy인 동안 전원을 내리면 안 되므로 확장에도 경고를 눈에 띄게 표시해 달라고 했다.
단순히 FTP 함수의 반환 시점에 경고를 지우면 제어기 내부 flash 쓰기가 끝났다는 증거가 없다. 공식 `Sync` 명령은 pending data가
모두 flash에 기록되고 flash 장치가 busy가 아닐 때까지 기다리며 DataID 910 `Disk Busy`가 0인지 확인하는 것과 같다고 명시한다.
또한 공식 FAQ·하드웨어 문서는 flash write/Flash Busy 뒤 전원 차단 전 최소 10초 대기를 안내한다. 따라서 안전 해제 조건을
`Sync` 종결 `STATUS 0` + 10초 안정화로 두었다.

### 구현

- `controller/deployment/flashSafety.ts`(순수) 신설: `writing → syncing → settling → safe` 흐름을 주입형 `sendSync`와 1초 tick으로 실행한다.
  `Sync`의 종결 STATUS가 없거나 0이 아니거나 전송·타임아웃 오류가 나면 `unknown`으로 끝내며 안전을 추정하지 않는다.
- `views/flashSafetyPresentation.ts`(순수) 신설: 모든 진행 단계에 「전원 끄지 마세요」를 넣고, `unknown`에는 물리 Flash Busy 표시가
  사라진 뒤 10초를 기다리라는 툴팁을 준다. `connectionStatusBar.ts`의 전용 high-priority 경고 항목이 이를 표시한다.
- `activation/deploy.ts`의 Save to Flash는 FTP 미러 시작 전에 경고를 켜고, 성공·변경 없음·취소·부분 실패 모두에서 `Sync` 안전 확인을
  시도한다. 확인 중에는 배포 잠금을 유지하고 `FLASH_SYNC`/`FLASH_SETTLE` 단계를 기록한다. 확인 성공 뒤에만 경고를 지우며,
  실패하면 「FLASH 안전 상태 미확인」 상태로 남긴다.
